# Internationalization (i18n)

OpenBin's client uses [react-i18next](https://react.i18next.com/) for translations, with English (`en`) and Norwegian Bokmål (`nb`) as the supported locales. Every feature folder except `src/features/legal/` and `src/ee/` (both out of scope, see Roadmap) is migrated. The `nb` translations have not had a native-speaker review yet (see Roadmap). New code must not add hardcoded user-visible strings: CI lints for them (see "Extraction and lint tooling").

## Namespaces

One namespace per feature folder, named after the folder in camelCase (`shopping-list` → `shoppingList`, `bulk-add` → `bulkAdd`): `activity`, `admin`, `ai`, `areas`, `attachments`, `auth`, `bins`, `bulkAdd`, `capture`, `checklist`, `checkouts`, `common`, `dashboard`, `items`, `locations`, `onboarding`, `photos`, `print`, `qrcode`, `reorganize`, `settings`, `shoppingList`, `tags`, `tour`, `usage`. Plus `errors`, which holds the generic translated messages for server error codes (`errors:codes.*`, used by `getErrorMessage()` in `src/lib/utils.ts`). The foundational ones:

- **`common`** (`src/locales/{lng}/common.json`) — shared layout chrome (`src/features/layout/`: sidebar, bottom nav, mobile drawer, create-FAB, app shell) **plus** generic cross-cutting strings used across the whole app: `actions.save`, `actions.cancel`, `actions.delete`, `actions.loading`, `actions.confirm`, etc. Other namespaces reuse these generic keys (`t('common:actions.save', ...)`) instead of defining their own. It also holds the localized default terminology (`common:terms.*`).
- **`auth`** (`src/locales/{lng}/auth.json`) — everything under `src/features/auth/`: login, register, forgot/reset password, complete-signup, social buttons, OAuth error toasts, consent checkboxes.

`common` and `errors` are preloaded on app boot (`src/lib/i18n.ts`'s `ns`) so the app shell and error toasts never flash untranslated keys. Every other namespace lazy-loads via `i18next-resources-to-backend` when first used.

Each migration PR that adds a namespace adds its JSON file for every locale and updates `src/i18next.d.ts`'s `resources` type (see below). Nothing else needs registering: the app lazy-loads any `src/locales/{lng}/{ns}.json`, and the test helpers glob them.

## Adding a new string

1. Add the key to the right `src/locales/en/{ns}.json` and mirror it in `src/locales/nb/{ns}.json` (`src/test/__tests__/localeParity.test.ts` fails CI if the key sets differ).
2. In the component: `const { t } = useTranslation('common' | 'auth');` then `t('some.key')`.
3. Pass a `defaultValue` when the string also needs to render sensibly under the test mock (see Testing below): `t('some.key', { defaultValue: 'English text' })`.
4. If you're adding a **new namespace**, update `src/i18next.d.ts`'s `resources` map so `t()` calls stay type-checked against the real JSON shape.
5. If your file uses `useTerminology()` (the admin-configurable "bin"/"tote"/etc. term system), destructure it as `term`, not `t` — `const term = useTerminology();` — to avoid colliding with i18next's `t`. `useTerminology()` itself is a separate, non-i18n system (see "Known limitations" below); it isn't part of `common`/`auth` and doesn't need translation keys.

Nested JSON objects are the convention (e.g. `auth.login.emailLabel`), not flat dotted-string keys — this is idiomatic for i18next namespaces and lets `src/i18next.d.ts` generate a properly-nested key type.

## Extraction and lint tooling

This repo uses [`i18next-cli`](https://github.com/i18next/i18next-cli) (the maintained successor to `i18next-parser`), configured in `i18next.config.ts` at the repo root:

```sh
npx i18next-cli lint      # same check CI runs — flags hardcoded strings, missing/unused keys, interpolation mismatches
npx i18next-cli extract   # scans source for t()/useTranslation() calls and updates the JSON resource files
```

`i18next.config.ts` scans all of `src/` (minus tests, and minus `src/features/legal/` and `src/ee/`, which are out of scope — see Roadmap). Strings in folders that haven't been migrated yet are recorded in **`i18next-lint-baseline.json`**: the linter matches baseline entries by file and string text (not line number), so CI fails only on *new* hardcoded strings anywhere in scope.

After migrating strings, shrink the baseline and commit it:

```sh
npx i18next-cli lint --update-baseline
```

`lint` prints a "baseline entries no longer occur" notice when strings were migrated but the baseline wasn't refreshed; that's not a failure, but keep the file current so it stays an accurate to-do list (`jq 'map_values(add)' i18next-lint-baseline.json` gives per-file counts).

The linter only sees JSX text and translatable JSX attributes (`aria-label`, `placeholder`, `title`, `label`, ...). Strings in plain JS — toast messages, `label:`/`title:` properties in config arrays, error messages — are **not** in the baseline, so each migration PR has to grep its folder for those too.

## Adding a new locale

1. Create `src/locales/{code}/` with one JSON file per namespace in `src/locales/en/`, mirroring their key structure (the parity test enforces this).
2. Add `{ code, label }` to `SUPPORTED_LANGUAGES` in `src/lib/language.ts` — `label` should be the language's **native** name (e.g. `"Norsk (bokmål)"`, not `"Norwegian"`) so users can find their language regardless of the app's current display language.
3. Add the code to the server's hardcoded allowlist in `server/src/routes/auth/profile.ts` (`SUPPORTED_LANGUAGE_CODES`) — `PUT /api/auth/profile` rejects any `language` value not on this list. A DB-configurable list was considered and rejected: with only a couple of locales, adding one more means shipping translation JSON anyway (a code change regardless), so a configurable list would solve a problem that doesn't exist yet.
4. If the locale is RTL (Arabic, Hebrew, Persian, Urdu, ...), add its code to `isRtlLocale()` in `src/lib/language.ts` — this flips `document.documentElement.dir`, but note that's the *only* RTL support that exists today (see Known limitations).

## Known limitations

- **`useTerminology()` composition.** Admin-configured term pairs (e.g. renaming "bin" to "tote") are plain text substitutions, not CLDR-aware. The default terms are translated (`common:terms.*`: nb "boks", "sted", "område"), but a customized term is used verbatim. Product nouns are always interpolated (`{{bin}}`, `{{bins}}`, `{{Bin}}`, `{{location}}`, `{{area}}`…), never hardcoded in a translation, so a custom term shows up everywhere. In Norwegian, gendered articles and adjectives in front of a term placeholder ("en {{bin}}", "Ny {{bin}}") can disagree with a custom term's gender; strings were phrased to avoid this where possible, but some remain.
- **The admin panel uses fixed nouns.** `src/features/admin/` is instance-wide, so it says "Bins", "Locations" and "Areas" as plain translated text rather than using the active location's custom terms.
- **Server error messages.** `getErrorMessage()` shows a generic translated message for known error codes (`errors:codes.*`) when the UI is not English. `VALIDATION_ERROR` and codes without a translation (e.g. `OVER_LIMIT`, `MALWARE_DETECTED`) still show the server's English text. Translating those needs server-side changes (structured error params).
- **Pluralization.** Only i18next's built-in CLDR plural suffixes are used (`itemCount_one` / `itemCount_other`), which covers English and Norwegian (both simple 2-form plural languages). No ICU MessageFormat plugin (`i18next-icu`) yet — add it if/when a complex-plural locale (Arabic's 6 forms, Polish's 4, etc.) enters scope.
- **Dates and numbers.** Use the active locale: `new Intl.DateTimeFormat(i18n.language, {...})` inside `useMemo(..., [i18n.language])`, not module-level instances and not a hardcoded `'en'`/`'en-US'`.
- **RTL layout.** Only `document.documentElement.dir` is wired (pre-paint script in `index.html` + `setLanguage()` in `src/lib/language.ts`). No Tailwind `rtl:` variants, no icon/flex-direction mirroring anywhere in the app. Full RTL layout is a separate future epic.
- **Transactional emails are not covered, ever.** Password reset, invite, and account-deletion emails (sent via Resend) are generated server-side where no client `i18next` instance exists. This framework does not cover them now, and nothing planned covers them — email localization would need its own future epic with server-side translation infrastructure.

## Testing

- **Default (mocked) — most component tests.** `src/test-setup.ts` mocks `react-i18next` globally: `useTranslation()` returns a `t` that resolves `(key, opts) => opts?.defaultValue ?? key`. This keeps the hundreds of existing component tests fast, without needing real translation resources loaded — but it means call sites that need to render sensible text under test **must** pass `defaultValue`, e.g. `t('login.signIn', { defaultValue: 'Sign In' })`. The mock fills `{{var}}` placeholders in `defaultValue` from the options and, given a `count`, uses `defaultValue_one`/`defaultValue_other`, so write whole translatable sentences with interpolation (`t('added', { defaultValue: 'Added {{count}} items', count })`) rather than concatenating fragments. For plurals, pass `defaultValue_one` and `defaultValue_other` and add `key_one`/`key_other` to the JSON.
- **Real resources — `renderWithI18n()`.** `src/test/i18nTestUtils.tsx` spins up a dedicated i18next instance (via `createInstance()`, isolated from the app's own `src/lib/i18n.ts` singleton) with every `src/locales/*/*.json` loaded synchronously (via `import.meta.glob`, so new namespaces need no registration), and renders through a real `<I18nextProvider>`. Use this to catch broken keys, missing interpolation vars, or JSON typos that the mock wouldn't — see `src/test/__tests__/i18n.test.tsx` for real-render and pluralization examples. Since the global mock above applies file-wide via `test-setup.ts`, call `vi.unmock('react-i18next')` at the top of any test file that uses `renderWithI18n()`.
- No Suspense-boundary wrapping is needed in tests (`react: { useSuspense: false }` in `src/lib/i18n.ts`).

## Roadmap

### Status

Migration is complete for everything in scope: 26 namespaces, with `en` and `nb` key sets kept identical by `src/test/__tests__/localeParity.test.ts`. The lint baseline (`i18next-lint-baseline.json`) holds only the strings that were deliberately left, if any.

### Remaining

- **Norwegian review.** The `nb` files were written without a native-speaker pass. Review all of `src/locales/nb/*.json` for tone, consistency of vocabulary (e.g. "boks"/"sted"/"område", "gjenstand", "stikkord"), and the places where a term placeholder sits next to an article or adjective (see Known limitations).
- **Adding a language** — see "Adding a new locale" above.

### Out of scope

- **`src/features/legal/`** — legal prose stays English (translations would need legal review).
- **`src/ee/`** — separately licensed cloud/billing UI.
- **Transactional emails** — see Known limitations.

### Conventions for new features

Add the namespace JSON (en + nb), translate JSX *and* plain-JS strings (toasts, `label:` properties, error fallbacks — the linter only sees JSX), interpolate the configurable nouns instead of writing them, use `_one`/`_other` plural keys instead of `pluralize()`/`n !== 1 ? 's' : ''`, format dates and numbers with `i18n.language`, destructure `useTerminology()` as `term`, add a `renderWithI18n()` smoke test, update `src/i18next.d.ts`, and run `npx i18next-cli lint --update-baseline`. For strings authored outside any component (plain data/config files), thread a `TFunction` through as a parameter or context field — see `TourContext.t`, `describeAction()` and `mapAiError()` for the established patterns.
